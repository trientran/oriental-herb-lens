Herb Lens · migration plan · revision 3

From one XML Android app to Android, iOS and web on shared Kotlin

Revision 3 (5 Oct) adds the iOS app, account deletion, geotagged uploads, contributor records on users/{uid} and the reworked Pick a plant (§01). Revision 2 recorded Phases 0 and 1 as done and adds the decisions made since: the species CSV is the single source of truth, the medicinal content is removed, Firestore keeps only photo URLs and Vietnamese name suggestions, photos come from R2 and GBIF, and herb identification stays on ML Kit on both platforms.

01

What changed in revisions 3 and 2

Revision 3 (5 Oct)

  • The iOS app runs on an iPhone (Phase 5, #10): the same Compose UI, with Swift bridges for ML Kit, Google Sign-In and Sign in with Apple. ML Kit works on devices only; the simulator gets stubs.
  • Contributors are recorded on users/{uid}: uid, and name and email when the provider shares them (Apple shares neither), written once per user and device. The rules let users write only these fields on their own document, with the email they signed in with. The collection stays: it's also where favourites and history could sync later (D9).
  • Accounts can be deleted in the app (App Store guideline 5.1.1(v)): after signing in again, the app deletes users/{uid}, revokes Apple tokens for Apple accounts, and deletes the Firebase account. Shared photos stay, no longer linked to an account (D11).
  • Every photo upload needs a place (geotagged research records, D10). Enforced in the app; the rules can't inspect the JSON detail strings.
  • Pick a plant reworked on both platforms (D12): a dot on each plant; holding the camera on one for 2 seconds, or tapping its dot, shows the cropped plant with its results and pauses the camera. Whole view identifies the centred square the user sees, not the whole frame stretched to the model's 224 × 224 input.
  • The Firestore rules were deployed on 5 Oct, before the new app shipped (see §12).

Revision 2 (4 Oct)

  • Phases 0 and 1 are done and merged into develop (#3, #4). See §10 for what each delivered and what was deliberately deferred.
  • The species CSV is the single source of truth for everything the app shows about a species: scientific name, authorship, family, genus, Vietnamese and English names. The app is offline-first: browsing, search and identification work without a network.
  • Medicinal content is removed. The overview, dosing and caution tabs go, because there are no herbal specialists or traditional physicians to validate that information. Reviews were already removed in Phase 1.
  • Firestore keeps only two kinds of data: photo URLs per species (the herb document ID is the GBIF species key) and Vietnamese name suggestions, which only the project admin reads.
  • Photos come from two sources: user uploads stored on R2, and research-grade photos from the GBIF occurrence API, shown with their creator and licence.
  • Herb identification stays on ML Kit (custom image labelling with the bundled or downloaded .tflite) on Android and iOS. Earlier revisions proposed switching to LiteRT; that's dropped. LiteRT is considered only for the user-trained models feature (Phase 7).
  • Phases are renumbered. The data-model changes ship first in the Android app (new Phase 2); extracting KMP modules becomes Phase 3. Everything after shifts by one.
  • R2 is live on its r2.dev public URL. A custom domain is recommended before user photos are served at scale (§04).

03

Module graph

Dependencies only point downward, with one exception: core:data depends upward on core:domain because it implements the domain's repository interfaces. Feature modules never see core:data. Only the app shell connects the two, through Koin.

platform entry point shared module (commonMain + platform code where noted) pure Kotlin, no framework later / gated / test-only

Rules enforced in CI

  • core:domain depends only on core:common and kotlinx-coroutines. It must not reference Android, Firebase, Compose, Ktor or SQLDelight.
  • feature:* depends on core:domain, core:designsystem, core:maps and core:common. It never depends on core:data or any source module. One exception: feature:scan may use core:ml on Android, because camera frames go straight to ML Kit.
  • Classes in core:data and the source modules are internal. Each module exposes only a Koin module { }.
  • core:common and core:domain also compile for wasmJs and js from Phase 3 onward. That keeps both web options in §09 open at no cost.
  • core:testing is added only through commonTest, so it never ships in a production build.

Presentation pattern

abstract class MviViewModel<S, A>(initial: S) : ViewModel() {
    private val _state = MutableStateFlow(initial)
    val state: StateFlow<S> = _state.asStateFlow()          // the only thing the UI observes
    abstract fun onAction(action: A)                          // the only way the UI talks back
    protected fun setState(reduce: S.() -> S) = _state.update(reduce)
}

@Composable fun HerbDetailsRoute(vm: HerbDetailsViewModel = koinViewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()
    HerbDetailsScreen(state, vm::onAction)                    // stateless, previewable, testable
}

One-off UI messages (a snackbar, for example) are stored in state as userMessage and cleared with a MessageShown action. Navigation calls are passed down to the Route as lambdas. So there's exactly one stream per screen. Use cases exist only where there's real logic, such as RecognizeHerb, SyncContent, SearchHerbs, SubmitImages and SuggestVietnameseName. A use case that just forwards one call to a repository is skipped.

04

Content delivery: R2, Remote Config and DataStore

This replaces the current MainActivity.downloadModel() code. That code downloads from Firebase Storage into cacheDir, which the OS is allowed to clear, while SharedPreferences keeps pointing at the deleted file. The same pipeline delivers both the model and the CSV catalog.

Remote Config keys

  • herb_model_url, herb_model_sha256
  • herb_catalog_url, herb_catalog_sha256
  • min_supported_version_android / _ios
  • recommended_version_android / _ios
  • catalog_source, search_source (migration flags; removed afterwards)

The version keys replace mustUpdateAndroid and shouldUpdateAndroid, which are read from Firestore today.

R2 setup (live)

  • Bucket herb-lens-content, served today from its r2.dev public URL. That URL is rate-limited and uncached: fine for model and catalog downloads, which happen only when a version is published, but switch to a custom domain before user photos are served, since every photo view hits it.
  • Versioned file names that are never overwritten, e.g. models/herb_model-20261001-ab12cd34.tflite and catalog/herbs-20261001-5d62fb66.csv, with Cache-Control: public, max-age=31536000, immutable
  • tools/publish_content.py validates, uploads, re-downloads to verify, and prints the Remote Config values. Setup and rollback: docs/content-publishing.md.
  • R2 charges nothing for egress (download bandwidth).

Sync algorithm (SyncContentUseCase, built in Phase 1)

  1. On launch and whenever the app returns to the foreground, fetch and activate Remote Config. The existing 1-hour minimum fetch interval still applies.
  2. For each file (model, catalog): if the Remote Config URL equals the installed URL stored in DataStore, stop.
  3. Otherwise download to content/<name>.download in app storage: filesDir on Android, Application Support on iOS (excluded from iCloud backup). Android runs this as a unique WorkManager job that needs a network connection; iOS uses a background URLSession.
  4. Check the file. The SHA-256 must match. The model must load in a throwaway interpreter. The CSV must parse and match the expected schema.
  5. Activation check: every label the model outputs must exist in the catalog that will be active. If the new model arrives before its matching catalog, keep it waiting until the catalog arrives.
  6. Swap in the new file. The model is renamed over herb_model.tflite (same name, as you decided). The catalog is imported into staging tables and swapped in within one database transaction.
  7. Save the installed URL and checksum to DataStore, then emit a new ContentVersion. The classifier switches to the new model between frames, never during one.
  8. If any step fails, keep the current files and retry with backoff. The working copy is never deleted. If a downloaded model fails to load at startup, fall back to the bundled model and clear the stored URL.

Where labels come from. The model's label list (GBIF species keys) travels inside the .tflite file as TFLite metadata. A model with metadata is also a valid zip file with labels.txt inside, so the model and its labels always change together. Phase 1 reads it with java.util.zip for the activation check; iOS will do the same in Swift. ML Kit reads the same metadata for inference on both platforms.

Publishing a new version: a small script run from your machine computes the SHA-256, uploads the file to R2, and then updates the two Remote Config keys. Always upload first and update Remote Config second, so no client is ever sent a URL that doesn't exist yet.

05

Herb catalog and Vietnamese search

Algolia currently handles diacritics, typos and highlighting for you. The replacement is shared Kotlin that works the same on Android, iOS and the web, and it gets a fixed set of test cases so it can't get worse than Algolia without a test failing.

CSV contract

  • The file is a GBIF species export plus a vietnameseName column: 4,799 species today, covering every one of the model's 2,721 labels. The app reads speciesKey (the ID everywhere), canonicalName, authorship, family, genus, vernacularName (English) and vietnameseName, and ignores the other columns.
  • Name columns hold several names separated by ; or ,; the first is the preferred one. Separators inside parentheses don't split a name.
  • UTF-8 with RFC 4180 quoting. The publish script normalises text to Unicode NFC; the app normalises again on import, because the original label data was mostly decomposed (NFD).
  • A copy is bundled in the app and used until a newer one is installed through §04.

Folding: one character in, one character out

VietnameseText.fold() lowercases, maps each Vietnamese vowel with any tone or vowel mark (all 134 precomposed forms) to its base letter, maps đ/Đ → d, and turns punctuation into spaces. Unicode normalisation doesn't remove the stroke on đ, which is why it needs its own rule. Kotlin's shared standard library has no Normalizer, so this is a lookup table, about 150 lines with tests. Because every character maps to exactly one character, a match position in the folded text is the same position in the original. That's how we keep Algolia-style highlighting. Queries can also arrive decomposed (combining marks U+0300–U+036F), so those marks are simply dropped from queries.

Storage and ranking

  • SQLDelight table herb_search(id, vi_folded, latin_folded, aliases_folded, en_folded), filled in during import.
  • A query first narrows the rows with LIKE '%' || :token || '%' on the folded columns. HerbSearchRanker in core:domain then scores the results. Order: exact name, then the name starts with the query, then every query word matches the start of a word (in any order; Vietnamese before Latin before English), then a match anywhere in the text, then a match allowing one typo (Damerau-Levenshtein distance 1, only for words of 4 or more characters). Ties go to the shorter name, then alphabetical order.
  • Why not SQLite FTS5: the system SQLite on Android devices down to minSdk 26 doesn't guarantee FTS5. Its remove_diacritics tokenizer doesn't fold đ. And a catalog of this size doesn't need a full-text index. Measure on a large test catalog, and switch to FTS4 over the same folded columns only if it's too slow.

Security rules (sketch)

The deployed rules, with emulator tests, are in firebase/firestore.rules and firebase/test/rules.test.js; they add the users/{uid} rules below to this sketch.

rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function writer() {
      return request.auth != null
        && !exists(/databases/$(db)/documents/bannedUsers/$(request.auth.uid));
    }
    match /herbs/{speciesKey} {
      allow read: if true;
      // Only the images map may change, and existing photos can't be removed or altered.
      allow create, update: if writer()
        && request.resource.data.diff(resource == null ? {} : resource.data).affectedKeys().hasOnly(['images'])
        && (resource == null || request.resource.data.images.keys().hasAll(resource.data.images.keys()))
        && request.resource.data.images.size() <= 1000;
    }
    match /nameSuggestions/{id} {
      allow create: if writer()
        && request.resource.data.keys().hasOnly(['speciesKey','viName','uid','createdAt'])
        && request.resource.data.uid == request.auth.uid
        && request.resource.data.viName is string
        && request.resource.data.viName.size() > 0 && request.resource.data.viName.size() <= 100
        && request.resource.data.createdAt == request.time;
    }
    match /{document=**} { allow read, write: if false; }
  }
}

Bans are enforced by the rules (a bannedUsers/{uid} document), not by a client-side check. App Check stays enforced: each debug device's token must be registered once (it survives relaunches and updates, not uninstalls).

Rollout order matters. Installed versions still write names, reviews and favourites, and still read config/mobile. Ship the new version first, then set mustUpdateAndroid = true in config/mobile so old installs are forced to update, and only then deploy these rules.

Photos

  • User uploads go to R2 through a Cloudflare Worker: the app sends the compressed JPEG with the user's Firebase ID token; the Worker verifies the token, stores the file as photos/{speciesKey}/{uuid}.jpg and returns its URL; the app then adds the URL to herbs/{speciesKey}.images. No R2 credentials ship in the app.
  • GBIF photos come from api.gbif.org/v1/occurrence/search?mediaType=StillImage&taxon_key={speciesKey}, keeping media whose URL ends in original.jpg or original.jpeg (in a sample, all were iNaturalist photos). The photo strip loads the medium.jpg variant (about 500 px; small.jpg looked soft on iPad) and full screen the large.jpg one (about 1024 px): originals are slow to fetch from Australia.
  • Credits are required: most GBIF photos are CC BY-NC, the rest CC BY. The full-screen viewer shows creator, licence and source, linking to the occurrence record. CC BY-NC also rules out commercial use of those photos.
07

UI redesign

The redesign happens screen by screen during Phase 3, not as a separate project. The design system comes first, so every Compose screen is built in the new style from the start.

Visual language

  • Material 3 with a custom botanical colour scheme: deep leaf-green primary, sage secondary, turmeric-amber tertiary (for highlights such as confidence chips), and warm off-white surfaces. There's a matching dark theme. Android's dynamic colour is off by default, so herb photos always sit on the brand colours.
  • Be Vietnam Pro font, open-licensed and designed so stacked Vietnamese marks like ặ and ổ render cleanly. Latin names are always italic, following botanical convention.
  • Shared spacing, shape and elevation values, and a shared component set: HerbCard, ConfidenceChip, SectionCard, EmptyState, ErrorState, and remote images loaded with Coil 3.
  • Shared-element transition from a list item to its herb details screen.

Structure

  • Four destinations: Identify, Browse (with the search bar at the top), Saved (favourites and history), Profile (contributions and settings).
  • Species details: a photo carousel (user and GBIF photos, each credited), the Vietnamese name, the scientific name in italics with its authorship, family and genus, all Vietnamese and English names, a link to the species on GBIF, a map of where user photos were taken, and "Suggest a Vietnamese name". No medicinal content.
  • Identify: camera preview filling the whole screen. Results appear in a bottom sheet on phones and a side panel on tablets and desktops. Results below the confidence threshold are never shown.
  • Browsing and searching work without signing in; sign-in is needed only to contribute (D6). The app follows the system language (Vietnamese or English), and Android 13+ lets users choose a different language for this app only.

08

User-trained models (Phase 7)

Two separate features. Herb identification keeps ML Kit and your published model. User-trained models are a general tool: people train their own image classifier, in any field, on their own photos. Only that feature uses LiteRT, and it must work on Android, iOS and the web.

Why embeddings matter. A model's labels (the species keys in yours) are its final output. An embedding is the model's internal summary of an image, about 1,280 numbers taken just before the final layer. Training on a device is practical only if you keep a pretrained "backbone" fixed and train a small new final layer on those embeddings: seconds on a phone instead of hours. ML Kit returns labels only, which is why this feature needs LiteRT.

PlatformBackbone (embeddings)Training the final layer
AndroidLiteRTShared Kotlin (softmax classifier with Adam, L2 regularisation, early stopping)
iOSLiteRT through SwiftThe same Kotlin code, compiled with Kotlin/Native
WebLiteRT.js or TensorFlow.js (WebGPU, WebAssembly fallback)Kotlin/Wasm or the TF.js layers API, depending on the §09 decision
  • Backbone: a general-purpose image model with an embedding output (e.g. an EfficientNet or MobileNet feature extractor), published through the same R2 / Remote Config pipeline as the herb model.
  • What gets saved: a small "model pack": the backbone's checksum, the class names, the trained weights and accuracy figures. It works on every platform and can be exported and shared.
  • To confirm in a spike before any feature work: embedding speed and training time on a low-end Android phone, an older iPhone and a laptop browser, and how LiteRT is called from Kotlin on iOS and web.
